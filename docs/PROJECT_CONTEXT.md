### 校园网页窗口（2026-10-19，用户已同意并实施）

用户同意客户端内校园网页方案。本轮复用现有导航入口，学校 HTTPS 链接在独立原生窗口打开；使用当前账号的 Cookie 和直连 / WebVPN 路径。每个窗口使用独立临时浏览数据，主界面、其他账号和系统浏览器互不共享；Cookie 通过原生接口导入，不把密码、业务令牌或 Cookie 写入网页脚本。窗口没有启动器 IPC 权限。

同一账号重复打开校园链接复用窗口；站内新窗口链接在当前校园窗口打开。切换账号、移除当前账号、重新认证、退出或关闭主窗口时关闭校园窗口。系统菜单提供后退、前进、刷新及在系统浏览器打开；非校园链接保留系统浏览器行为。

目前仅支持标准 443 端口的学校 HTTPS 网页；浏览窗口内新获得的站点会话不写回账号文件，关闭后重新从加密账号会话恢复。学校 MFA / 会话过期仍按网页要求处理；依赖独立弹窗及 opener 通信的站点尚未适配。原生 Cookie 导入与账号隔离测试通过，真实校园网站逐站认证和 Windows 实机仍待验收。分支为 `codex/campus-browser`。

此前建议已获用户同意并实施为上方独立原生校园窗口，学校额外认证仍需遵循。参考 XJTUToolBox 的系统浏览器场馆支付流程同样提示先在浏览器登录，未找到通用跨浏览器免登实现。

## 1. 项目定位与用户

构建一款本地运行、可扩展的桌面启动器，先支持 macOS 和 Windows，主体共享一套代码，结合校园账号管理、自定义主页、Agent 和插件。优先服务学生，从西安交通大学校园场景切入，希望成为学生常用的应用。

校园网站入口分散，常用数据和操作往往藏得很深。应用通过插件集中提供便捷功能，例如课表查询、成绩查询、一键评教。具体校园功能暂不逐项展开；V0.1 首个校园插件先实现课表。

项目主体需要提供承载这些功能的通用能力。学校账号认证是访问个人校园数据与业务的基础；账号管理本身也是产品的重要组成部分。

“启动器”的当前明确形态是带主页和侧边栏的桌面应用。快捷键唤出、命令搜索、启动本地应用等能力尚未确定，不能仅凭名称推导为需求。

## 2. 主界面与侧边栏

打开软件首先显示可 DIY 的主页。侧边栏顺序如下：

| 位置 | 内容 | 当前要求 |
| --- | --- | --- |
| 第一个 | 主页 | 固定位置，进入自定义主页 |
| 第二个 | Agent | 固定位置，进入 Agent |
| 中间 | 插件入口 | 用户自定义展示的插件及排列顺序 |
| 倒数第二个 | 插件市场 | 固定位置 |
| 最后一个 | 账户设置 | 固定位置，校园账户登录、配置 API Key |

插件市场是明确的产品入口，默认提供几个插件供下载，并支持自动安装其中指定的默认插件。默认插件清单、自动安装时机和更新方式尚未确定。

用户明确不做的是启动器账号服务端；插件市场可以有自己的服务端。先完成启动器，插件市场服务端的具体实现放到后续讨论。不得将账号服务端的边界扩大为禁止其他服务端，也未决定采用静态目录作为最终方案。

## 3. 可 DIY 的主页

用户明确希望同时支持以下三类定制：

- **外观**：壁纸、背景、配色等。
- **内容**：快捷入口、小组件、插件提供的内容等。
- **布局**：拖动位置、调整大小、排列和分栏。

V0.1 先实现寄语、配色、组件显隐与顺序，本地保存；壁纸和自由布局留在后续完整 DIY 中实现。不能据此默认需要任意代码编辑、多设备同步等未讨论能力。

## 4. 插件的产品形态

插件可以提供以下一种或多种能力：

| 形式 | 用途 | 示例，仅用于说明 |
| --- | --- | --- |
| 独立页面 | 从侧边栏进入完整功能 | 完整课表页面 |
| 主页小组件 | 在主页展示信息或提供入口 | 今日课程 |
| Agent 工具 | 供 Agent 调用业务能力 | 查询课程 |

用户暂时认可上述三种形式，当前无需继续枚举其他扩展场景。

校园业务可以通过插件实现。V0.1 实现本地声明式插件加载，预置课表清单及 Rust provider；完整运行时和权限协议仍需后续设计。“通过插件实现”不等于已经决定某种动态加载技术。

插件、MCP 与 Skill 均需要支持，但三者之间的包装、注册、安装与调用关系尚未设计。

## 5. 账号与 API Key 管理

账户设置集中提供校园账户登录和 API Key 设置。用户于 2026-10-19 最新补充要求支持多个校园账号，更新此前取消多账户的决定；仍不做启动器自身的个人账户或保存用户账户的启动器服务端。

### 已明确的期望

- 支持添加和管理多个校园账号，查看各账号基础信息并配置头像。
- 添加账号使用应用自己实现的校园登录表单和提交逻辑；最新授权下已按批准的客户端风格接入页内表单。
- 添加账号时先检测目标校园服务能否访问，不能访问时直接进入 WebVPN 登录流程。
- 访问校园业务时，需要取得相应学校账户的认证状态。
- 用户可以配置 API Key。

需要持久化的校园登录状态、API Key、应用配置、Agent 聊天记录和记忆按本地数据管理。模型 API 和远程 MCP 的接入不要求建设启动器账户服务端。

### 仍需研究或设计

- 学校 SSO 的协议、登录与登出流程、会话检测及失效处理。
- 密码与会话均已支持本地加密保存；真实账号登录、重启恢复仍需验收。
- 不同校园系统能否复用认证状态，是否需要 WebVPN。
- 登出或重新登录后，校园业务页面与缓存如何刷新和清理。
- API Key 对应哪些服务、模型与接口格式，是否支持多个配置。

沿用此前的凭据管理原则：使用操作系统安全存储能力管理需要持久化的敏感凭据，不把密码、令牌、Cookie 或 API Key 明文写入配置、日志或仓库。V0.1 使用 keyring 库接入 macOS 钥匙串和 Windows 凭据管理器。

Rust 驱动的校园认证、WebVPN、多账号、密码与会话加密存储已接入应用自有页内表单；旧远程登录窗口已移除。尚未通过真实学生账户验证，不能把后端接线当作最终需求已验收。

不设计独立平台注册系统、云端账户保存、平台个人空间或相应的同步服务。多个校园账号属于本地账号管理。

## 6. Agent、MCP、Skill 与记忆

### 已明确的能力

- 完整的通用 Agent 基础能力，包括对话、任务规划、工具调用、文件操作、命令执行、执行反馈和上下文管理等；这只是概括，不是穷举。
- 支持调用插件提供的工具。
- 允许用户接入 MCP 和 Skill。
- 保存聊天记录，并具备跨对话的长期记忆。

长期记忆是核心要求。新建对话后，Agent 仍应能够利用已记住的用户偏好、背景和重要信息，减少重复说明。自动提取与显式记忆的规则、记忆管理交互、存储和检索方案尚未确定。

用户强调 MCP、Skill 和记忆是启动器的特点与卖点，不是 Agent 能力范围的上限。不得据此把 Agent 简化为聊天或少量工具调用。通用基础能力由实现方研究整理，不逐项询问用户是否需要；具体运行时、执行机制与集成方案仍未选定。

### 知识与信息来源

用户之后可能维护多个校园知识库 MCP，方便学生使用，也希望接入社区相关 MCP，借鉴点点 AI 一类通过对话查找、整理信息的体验。

主体需要提供通用的 MCP 接入和使用能力。具体接入哪些知识库、社区或服务，由接入的 MCP 决定，无需在主体需求阶段逐项确认。

个人记忆与外部知识来源分别讨论：前者保存用户相关信息与对话积累，后者由 MCP 等扩展提供。具体数据存储和访问边界尚未设计。
