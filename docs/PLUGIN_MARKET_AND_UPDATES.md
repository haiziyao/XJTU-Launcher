# 插件服务端、市场分区与软件更新

更新时间：2026-10-19。用户提出的新要求与本轮建议分开记录；页面参考稿仍待确认。此次仅修订设计资料，没有改动应用界面或部署服务端。

## 用户明确要求

- 需要插件市场服务端；设置页保留服务端网址。
- 地址默认不可编辑，点击右侧“确认更改”，弹出危险提示并确认后才允许编辑。
- 市场分别展示校园功能插件、可下载安装的远端插件。
- 已安装插件可单独管理启用状态和显示状态。
- 希望提供软件更新能力。

## 本轮具体设计

市场提供“校园功能 / 远端市场 / 已安装”三个标签页。前两个用于发现和添加功能，第三个统一管理本地安装状态。

- 校园功能：学校相关插件分类；已在应用中内置的功能直接添加。尚未实现的功能不能显示成可下载安装。
- 远端市场：从所配置服务获取插件目录、介绍、版本和下载信息。支持搜索、下载进度、安装结果和可用更新。
- 已安装：包含校园和远端插件，支持打开、更新、卸载或移除，以及两个独立开关。`启用`控制插件运行和工具可用性；`侧栏显示`只控制导航入口，隐藏不等于停用。停用时不提供活跃入口，保留用户原先的显示偏好供重新启用时恢复。无独立页面的后台插件不显示此开关。

设置 → 插件服务：

1. 默认以普通文字展示 URL 和锁图标，右侧“确认更改”。
2. 点击后展示危险提示：“更改后，插件列表、下载和更新将来自新地址。不可信的服务端可能提供有害插件。”
3. “取消”保持原状；“了解风险，继续”解锁本次编辑。
4. 编辑时出现输入框、保存和取消。保存成功或取消后恢复只读，下次更改需要重新确认。
5. 提供“恢复默认地址”。默认正式地址在服务部署后指定，设计稿使用的 `plugins.example.com` 仅为示例，不写入应用配置。

本轮将“内置插件服务端”理解为：客户端预置官方服务端地址，远端服务负责目录、版本、下载包及更新元数据。服务端可独立部署，不要求启动器平台账号，也不把校园账号或密码交给市场服务。

修改插件源仅改变插件服务配置。应用自身的更新源及验证公钥独立配置，避免一次修改连带改变客户端程序的更新来源。已安装包保留来源信息，不因为另一个源出现相同 ID 就无提示替换。

## 软件更新方案

选用 Tauri 2 官方 Updater 插件。2026-10-19 已核对官方文档源文件：

```text
https://v2.tauri.app/plugin/updater/
https://raw.githubusercontent.com/tauri-apps/tauri-docs/v2/src/content/docs/plugin/updater.mdx
```

核实事项：

- 支持动态更新服务端或静态 JSON 更新清单；官方 Tauri Action 可以生成用于 GitHub Releases 的更新清单。
- `createUpdaterArtifacts: true` 生成更新产物。macOS 使用 App 的 tar.gz 归档；Windows 使用 MSI/NSIS 安装包及各自签名。
- 更新插件校验发布签名，此校验不能关闭。客户端内置公钥，发布流程使用私钥；这是软件更新校验，与校园密码的本地保存方案独立。
- 静态清单按操作系统和架构分别提供下载地址与签名，并包含版本号及可选更新说明。

拟定交互：设置 → 软件更新，展示当前版本、检查更新、自动检查开关。发现新版后展示更新说明，由用户点击“下载并更新”，展示下载进度及安装状态。按平台更新机制关闭/重启应用，执行前处理运行中的 Agent 和校园提交任务；不在任务执行中直接重启。

插件更新与软件更新分开：前者更新插件包；后者更新客户端本体。服务端可共用部署资源，API 和客户端设置保持独立。初期可使用静态更新清单，后续接自建更新服务，无需重写客户端更新交互。

当前项目尚未引入 Updater 依赖、配置发布公钥、创建发布流水线或托管更新清单。因此设计稿中的 0.1.1 只是展示“发现新版”状态，并不代表已有正式发布。

## 插件运行时与版本边界

目前本地插件协议仅支持导航清单和编译进应用的校园功能。远端下载目录与任意可执行插件运行时是两个不同实现任务。落地时先明确包清单、兼容版本、来源与安装目录；下载暂存、校验、原子安装后才标记为已安装，失败保留现有版本。

内置 Rust 校园适配在未引入独立运行时前随 App 更新；下载清单不能冒充已经支持运行任意远端 Rust 代码。后续可独立更新的业务插件需要与 Agent 工具共同使用宿主接口。
