## 一、目标与边界

**要解决的**：现在唯一的反馈渠道是 GitHub Issue 和 Q&A 页里的提问链接，要求提建议的人有 GitHub 账号、会写 Issue 模板。想收的是四类东西：功能建议、Bug、使用问题、文案与内容问题。

**v1 明确不做**：

- 不做公开反馈墙，不做评论、点赞、回复串。
- 不做附件上传（截图最容易带学号、成绩、课程表，v1 先不收；确实需要时让用户在 Issue 里补）。
- 不做账号体系、不做登录后跟踪进度。
- 不做第三方统计与客服 SDK。

## 二、两条入口

### 官网 `/feedback/`（P0）

- 与 `doc/qa/`、`community/` 同级，纯静态页 + 一个表单脚本，沿用 `styles.css`。
- 导航栏加「反馈」，页脚同步；Q&A 页底部「仍有问题？」处加一个指向本页的按钮。
- 访问地址：域名上线前是 `http://8.152.100.169/site/feedback/`，域名上线后是 `https://xjtu-launcher.cn/feedback/`。页面里的接口地址用相对路径（`api/feedback`），和现有 `app.js` 一样按 `document.baseURI` 解析，两处都能用。

### 应用内「设置 → 反馈与建议」（P1，下个版本）

- 侧栏「设置」里新增一项，页面复用同一套字段，提交走同一个接口。
- 自动带版本号、平台、架构，用户不用手写；官网表单靠 UA 推断平台，应用内直接用真实值。
- 与官网共用接口意味着应用也要发 HTTP 请求，**这一条受 P0 更新源影响**：目前官网与更新源都还是 `http://8.152.100.169`，反馈内容虽不含凭据，但明文可被中间人改写。P1 要不要等 HTTPS 就绪，需要你定（见「待确认」第 6 条）。

## 三、表单字段

| 字段 | 必填 | 规则 | 说明 |
| --- | --- | --- | --- |
| 类型 | 是 | 单选：功能建议 / Bug 反馈 / 其他 | Bug 时展开「复现步骤」 |
| 标题 | 是 | 4–60 字 | 列表里能一眼看出是什么问题 |
| 详细描述 | 是 | 10–2000 字 | 占主要篇幅 |
| 复现步骤 | 否 | ≤1000 字，仅 Bug 显示 | 出现频率、是否稳定复现 |
| 联系方式 | 否 | ≤100 字，邮箱或 QQ 微信 | 不承诺回复时限 |
| 环境 | 自动 | 网站：平台 + 页面地址；应用：版本 + 系统版本 | 用户不可改，不在表单里显示 |

页面只留一句提醒，不加别的解释小字：

> 不要填写密码、学号等个人信息。

表单底部一个复选框：「我知道这条反馈会保存在项目服务器上，保留 12 个月」，未勾选不能提交。

防机器人：一个 CSS 隐藏的 `website` 字段，填了就拒绝。**没有做「打开到提交少于 3 秒」的判定**——浏览器自动填充和手快的用户会被误伤，真被刷再补。v1 不上验证码。

## 四、提交体验

- 成功：只写「收到了，谢谢」和编号 `FB-20261111-7K3Q`（日期 + 4 位随机码），**不写回复时限**，也不承诺一定回复。
- 失败：写清楚是网络、限流还是服务问题，**保留已填内容**，不假装成功；不自动重试。
- 限流命中：显示「提交太频繁，10 分钟后再试」，不退化成通用错误。
- 提交过程中按钮禁用并显示「正在提交…」；**没有做 localStorage 的 60 秒冷却**，服务端按 Cookie 的 5 条 / 10 分钟已经够用，客户端再加一层只会在真正需要连提两条时碍事。
- 错误码由接口返回，页面翻成中文：`title` / `body` / `kind` / `consent` / `steps` / `contact` / `spam` / `too many` / `too large` / `storage` / `json`；网络失败单独一句，内容保留。

## 五、后端

在现有 `tools/site-api/site-api.py` 上扩展（Python 3.6 标准库，已在跑，`xjtu-site-api.service`，监听 `127.0.0.1:8788`）：

**接口**：`POST /feedback`

- body 为 JSON，上限 8 KB；超限 413，解析失败 400。
- 字段白名单 + 类型校验；未知字段忽略。
- 成功 `200 {"ok": true, "id": "FB-..."}`；服务端限流 `429 {"error": "too many"}`；落盘失败 `500`。

**存储**：`/srv/xjtu-launcher/stats/feedback/2026-11.jsonl`，按月一个文件，一行一条 JSON，只追加不覆盖。

**每条记录**：

```json
{"id":"FB-20261111-7K3Q","t":"2026-11-11T02:31:07Z","type":"bug","title":"…","body":"…","steps":"…","contact":"…","version":"0.6.6","platform":"macOS arm64","page":"/feedback/","ip":"sha256:1a2b3c4d","ua":"…"}
```

- `ip` 只存加盐 SHA256 前 8 位（与点赞的 `xl_voter` 同一套做法），用来识别刷屏，不落原始 IP。
- `ua` 原串截断 200 字符：复现问题需要它，但它不是身份信息。
- 正文里如果出现疑似凭据（`password=`、`Bearer `、32 位以上十六进制串）不拦截，只在审计日志里标记 `maybe_secret`，提醒之后清理。

**日志**：`stats/feedback.log` 每次一行（id、类型、长度、是否需要人工看），**不写正文与联系方式**，5 MB 轮转，保留 5 份，与现有日志一致。

**备份**：纳入 site-api 现有的 900 秒快照（`STATS_DIR/backups/`），保留份数同现有策略。

**容量与保留**：单月文件超过 5 MB 时按月内再分片；对外承诺「保留 12 个月，之后随月文件归档删除」。

**查看方式**：不提供网页端列表（避免做出半个后台）。你在服务器上 `tail`/`jq` 看；P1 再加 `tools/feedback-export.mjs`，把某月导成 CSV 供归档。

## 六、防滥用

| 层 | 规则 |
| --- | --- |
| nginx | 新 zone `xjtu_feedback`，每 IP **60 次/分钟**、并发 5，超出 429 |
| 应用 | 同一 `xl_voter` Cookie 10 分钟内最多 5 条 |
| 应用 | 同正文 SHA256 24 小时内去重，返回同一条编号，不重复入库 |
| 应用 | 长度上限、非 UTF-8 拒绝、字段白名单 |

校园网一个 NAT 出口后面同时有几百人，按 IP 限制必须放到「只有脚本会撞上」的量级——所以每 IP 60 次/分钟只是兜底（和下载网关 120 次/分钟同一思路），真正生效的是按浏览器的 Cookie 配额与内容去重。真被定向刷再上验证码或人工白名单，不提前把正常用户挡在外面。

## 七、隐私与说明

页面**不再**放一整段隐私小字，只保留一句复选框：「我知道这条反馈会保存在项目服务器上，保留 12 个月」。其余内容写进计划书与接口实现，不在页面上重复：

- 收什么：标题、描述、步骤、联系方式，以及自动带的版本、平台、页面地址；另存一个加盐 IP 摘要用于防刷。
- 用途：只用于改进这个项目；联系方式只用于回复。
- 删除：发邮件或在 GitHub Issue 里说一声，按编号删除。
- 不公开：反馈内容不会出现在网站上，除非你另外同意。

不写「我们绝不收集任何信息」这种与实现不符的话；不承诺回复时长以外的东西。
